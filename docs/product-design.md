## 1. 作品集视角下，这个项目要证明什么

这是 v3 最重要的一节。你花 30 天做这个项目，目的不是"有个东西"，而是**让面试官在 5 分钟内相信你具备这六种能力**。设计里每个决策都应该服务于其中至少一条。

| # | 要证明的能力 | 靠什么证明 |
|---|---|---|
| 1 | **能发现并收敛一个真问题** | 问题具体（秋招签约）、边界清晰（比对而非法律意见）、明确列出"不做什么" |
| 2 | **能用确定性方案解决本该用 LLM 解决的问题** | 范本比对引擎、规则引擎——可解释、可测试、零推理成本 |
| 3 | **知道 LLM 该放在哪、不该放在哪** | LLM 降级为可选增强，且只承担语义模糊判断；法条一律查库不生成 |
| 4 | **有工程纪律，不只是能跑** | 黄金测试集、精确率/召回率、单元测试、CI、数据 schema 校验、版本可追溯 |
| 5 | **把隐私当作架构属性而不是口号** | 无服务端、无遥测、断网可用、承诺可被逐行审计 |
| 6 | **能交付** | GitHub Pages 上有可用的活链接、README 能让人 3 分钟跑起来、有演示数据 |

### 最大的风险：被面试官当成"套壳 ChatGPT"

这是这个项目作为作品集最可能翻车的地方。面试官看到"AI + 合同检查"，第一反应是：

> "这不就是拼个 prompt 调个 API 吗？"

**你必须在 30 秒内给出否定的答案，而且是结构上的否定。** 你的回答应该是：

> 核心不是模型，是一个确定性引擎。我把当地人社部门的官方范本结构化建成带版本和出处比对库，把合同按条款切分、归一化，然后跟范本做对齐，输出四类差异——范本有合同没有、范本没有合同多了、关键条款被改写、填空留白。这些结论完全可复现、可解释、零推理成本、离线可用。大模型只在最后一层可选地做语义模糊判断，比如工资结构是否被拆成绩效从而压低加班费基数，而且它不负责输出法条——法条一律从库里取。

**这段话就是你的产品定位、技术架构和差异化。** 设计上要保证这段话字字属实，写代码时也要守住这个结构——一旦你把 LLM 变成主力，这个项目就真的变成套壳了。

## 2. 定位：范本比对

> **把当地人社部门的官方示范文本作为基准，逐条比对你手上的合同，把"该有的没有""不该有的多了"的地方指出来，并对照法律规定提示需要留意之处。**

为什么这个定位优于"AI 法律风险分析"：

1. **举证结构不同**。v1 说"我判断这条违法"是出具法律意见；v3 说"当地范本里有这条，你的合同没有"是客观事实陈述。
2. **工程上更硬**。差异是算出来的，可以写单测、可以算准确率——这正好是作品集需要的可验证性。
3. **风险恰好在差异里**。范本本身是合规的，风险集中在企业自加和改写的地方，比对正好把这个区域框出来。

### 产品主张

**"3 分钟，把你的劳动合同跟当地官方范本对一遍。断网也能用。"**

### 边界（写进 README，也是加分项）

不做法律意见、不预测仲裁结果、不代理、不承诺覆盖全部风险。重大疑虑引导至 12333 或执业律师。**清楚地知道自己在法律上的位置，本身就是专业素养的体现。**

## 5. 核心机制：范本比对引擎（技术亮点 1）

管线：

```
文件 → 解析 → 条款切分 → 条款归一化 → 与范本对齐 → 差异分类 → 命中规则 → 评分
```

### 5.1 条款切分
- 规则优先：按条款编号（`第X条` / `一、` / `1.1`）、按标题关键词（试用期、劳动报酬、工作时间、社会保险、保密、竞业限制、违约责任、解除）
- 无编号合同用启发式兜底（段落长度、标题特征、标点模式）
- **自检**：切分后字符总量应与原文长度接近，偏差超阈值即报错——这条校验能挡住最常见的静默失败

### 5.2 条款归一化
- 同义表述映射：`劳动报酬` / `工资` / `薪资` / `薪酬` → `REMUNERATION`
- 数值抽取与单位归一：`月薪 8000 元`、`8000元/月`、`税前 8,000`
- 输出：`{ normalized_type, raw_text, seq, page, char_range }`

### 5.3 对齐与差异分类
把合同的每个条款对齐到范本对应条款，输出四类差异：

| 差异类型 | 含义 | 默认等级 |
|---|---|---|
| `MISSING_IN_CONTRACT` | 范本有、合同没有（法定必备条款被删） | 🔴 |
| `EXTRA_IN_CONTRACT` | 范本没有、合同多了（**风险最集中**） | 🔴/🟡 |
| `MODIFIED` | 关键条款被改写，附带差异点 | 🟡 |
| `BLANK_LEFT` | 填空处留白、金额工时未填 | 🟡 |

**范本侧的填空位是通配符，不是文本。** 范本正文里有大量待填写位（`第 种方式`、`年 月 日`、`元`），抽取时被标记为 `{{FILL}}`（实现见 `src/mark-blanks.ts`）。比对时必须把范本条款编译成正则（`{{FILL}}` → `.+?`）再与用户合同匹配；若按字面比较，用户填好的每一处内容都会被判成 `MODIFIED`，误报率会高到不可用。

这条约束来自真实数据，不是推演——设计阶段完全看不出来，是拿到真实范本、跑通抽取之后才暴露的。这也是"先拿真实范本再设计比对算法"这个顺序的理由。

**这是整个项目的技术核心，也是最值得写进 README 用图讲清楚的部分。** 建议为它画一张架构图和数据流图——面试时看图讲比看代码快。

### 5.4 规则引擎（与比对新互补）
处理不依赖范本也能判定的硬性违法点：

试用期超法定期限 · 试用期工资低于约定工资 80% · 违法约定违约金（服务期与竞业限制之外）· 竞业限制超 2 年或无经济补偿 · 约定"自愿放弃社保" · 工资低于当地最低工资 · 加班费基数低于正常工作时间工资 · 缺少法定必备条款

**每条规则必须绑定法条 ID，报告中展示条文原文。** 规则用 JSON 声明，便于测试与社区贡献：

```
{ code, title, level, check_type, params, statute_refs, enabled }
```

`check_type` 枚举化（如 `NUMERIC_COMPARE`、`EXISTENCE`、`PATTERN_MATCH`），引擎只实现有限几种判定器——这样规则库可无限扩，代码不外扩。

### 5.5 评分（已废弃）

> **这一节已废弃。** 综合评分在 v0 上线后按产品定位删除了：权重是拍脑袋定的，而且一个宣称"不构成法律意见"的工具不该在最显眼处给出综合打分。现在报告只给标注计数，不做评价。理由见 `README.md` 的「报告层」一节。下面保留的是当时的原始设计，作为决策记录。
透明、可解释，不做黑盒：

```
score = 100 − Σ(红×15) − Σ(黄×5) − Σ(蓝×1)，下限 0
一票封顶：命中"违法约定违约金""未缴纳社保"直接 ≤ 40
```

并明确标注：**分数由差异与规则命中算出，不代表法律评价。**

## 6. 领域数据：版本化、可校验（技术亮点 2）

范本库、规则库、法条库是**这个项目真正的资产**，也是最容易被做成"随便凑的数据"的地方。v3 要求它们具备工程属性。

| 属性 | 要求 |
|---|---|
| 出处 | 每条必须带 `source_url` + `source_org` + `publish_date` |
| 版本 | 带 `version` 与 `effective_from` / `effective_to`，支持多版本共存 |
| Schema | 用 JSON Schema 或 Zod 定义，**CI 中强制校验**，格式错误直接挂构建 |
| 唯一 ID | 法条用稳定 ID（如 `LCL-25`），规则用 `code`，报告里引用 ID 而非文本 |
| 溯源 | 报告页显示"依据规则库 v0.3 / 范本库 2024 版" |
| 版权 | 政府行政性文件通常不受著作权保护（《著作权法》第五条），但仍须逐份标注来源与日期 |

**做法上的一个关键选择**：不要手工敲数据。写一个轻量的数据构建脚本（若能自动抽取就自动，不能就半自动 + 人工确认），产出 JSON 并跑校验。理由有两个：一是手工数据必然出错且不可复现；二是"我建了一条带溯源校验的数据管线"在面试里比"我录入了 3 个省"强得多。

**范本库只做 3 个省**（建议北京、上海、广东，覆盖生源与就业最集中的地区）。够证明机制，不浪费 30 天去堆覆盖度。

### 6.1 作者不具备法律专业背景时的规则准入标准

本项目作者不是法学专业。这不是缺陷，但必须把它转成一条架构约束，而不是靠自信掩盖。

**硬约束：系统里不允许出现任何一处依赖作者个人法律判断的内容。**

由此得到规则库的准入标准：

| 准入条件 | 说明 |
|---|---|
| **可溯源** | 依据必须是官方来源的条文原文，能给出处与生效日期。追溯不到的规则，不写 |
| **高确定性** | 只收条文表述明确、几乎无需解释的规则。例如试用期期限对照、竞业限制不超过 2 年、违约金的法定情形——判定是数值比较或存在性检查，不需要法学推理 |
| **可判定** | 判定逻辑必须是 `NUMERIC_COMPARE` / `EXISTENCE` / `PATTERN_MATCH` 这类确定性算子，不能是"模型觉得像" |
| **有单测** | 每条规则配正例与反例用例 |
| **宁可少，不可错** | 30 条可靠规则远胜 100 条半懂的规则。覆盖范围小只是产品局限，规则写错是产品失效 |

**明确排除以下类型**：需要价值判断的（"违约金数额是否过高"）、需要地方司法实践口径的（"加班费计算基数如何认定"）、需要解释法律概念的。这些宁可留给"建议咨询律师"的引导，也不要自己做。

这条约束有个很好的副产品：**产品定位与作者能力边界天然吻合**。系统只做"事实比对 + 条文引用"，而这两件事恰好都不需要法学知识——只需要能准确采集和引用公开的官方文本。所以"不是法学生"不会变成产品风险，最多让规则覆盖范围小一些。

**AI 在这里的正当用法**：可以让模型从条文原文里提出候选规则，但每条候选都必须由人回到官方原文逐字核对（条文真实存在、表述一致、未废止）。核对不了的候选一律丢弃。**AI 负责提候选，人只负责核对溯源**——把专业判断的负担压到最低，同时不牺牲可追溯性。

**轻量协作路径**（不需要聘请律师）：

- 本校的法律援助中心、法学社团、模拟法庭社团——一封邮件或一条私信即可，对他们是实践机会，对你是半小时的审校
- 在 GitHub 仓库开 issue 公开征集规则库审校（开源项目的天然协作方式）
- 若确实找不到人：**只做高确定性规则的版本依然成立**，项目不会因此停在半路

**面试时这个问题大概率会被问到，答案要点**：

> 正因为我不是法律专业，我给自己设了一条硬约束：系统里不允许出现任何一处依赖我个人的法律判断。所有法律内容必须来自官方来源并标注出处与生效日期，规则库里每条规则都要能追溯到条文原文，追溯不到的就不写。这样我的法学知识不足不会变成产品风险，最多是规则覆盖范围小一些。

## 7. 评估体系（技术亮点 3 — 最能拉开差距的部分）

**绝大多数求职作品集只有功能，没有评测。你只要把这一块做出来，立刻就和别人不在一个层级。**

### 黄金测试集
- 20~50 份真实劳动合同（脱敏），由人标注"存在哪些风险、等级、依据"
- 数据结构：`{ contract_id, risk_code, level, clause_ref, statute_ref }`
- 脱敏要彻底：姓名、公司名、身份证号、金额替换为占位符，但保持结构不变

### 指标
| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **召回率** | 已标注风险中被检出的比例 | **最重要**。漏掉一个"违约金违法"意味着用户签了，产品价值为负 |
| 精确率 | 报出的风险中真实存在的比例 | 误报损害可信度 |
| 条款切分正确率 | 切分边界与人工标注一致的比例 | 上游错误会污染全部下游结论 |
| 差异分类准确率 | 四类差异判定正确率 | 核心算法指标 |

### 工程化
- 评测脚本一条命令跑完，输出指标表（并提交进仓库，作为历史记录）
- 每次改规则或改算法都跑一遍，指标下降就不过
- **把指标写进 README**，这是最硬的可信度证据

### 面试话术（提前准备好）
> 我建了 30 份合同的标注集，当前召回率 92%、精确率 78%。我优先保召回率，因为漏报的代价远高于误报——漏掉一个违法违约金条款，用户可能真的签了。误报只是让他多问一句。

**这段话的信息密度极高：有数据、有取舍、有对用户后果的理解。** 比任何功能列表都有说服力。

## 8. AI 增强：LLM 放在正确的位置（技术亮点 4）

默认关闭，需要用户自己的 API Key，开启前明确告知。

### 只让它做这些
- 语义模糊项：岗位表述过宽（"公司可随时调整岗位"）、单方调岗调薪权、**工资结构过度拆分为绩效从而压低加班费与经济补偿基数**、解除条件超出法定情形、保密范围无边界
- 条款互相矛盾检查
- 沟通话术生成（"怎么跟 HR 提这件事"）

### 绝不让它做这些
- **输出法条**。法条一律从本地库取，LLM 只负责"从候选集里选哪一条"
- 生成风险等级之外的判断结论

### 引用校验（四重断言，必须实现）
1. `statute_id` 存在
2. `status = effective`（未废止）
3. 条文文本与库中原文逐字一致
4. 引用与该风险语义相关（可再用一次 LLM 复核）

任一失败即降级为"信息提示"或丢弃，并记录。**"我的系统不敢直接信任模型输出的法条"是一个非常好的面试回答。**

### 必须实测的技术前提
浏览器直连大模型 API 通常被 **CORS** 拦截。**第 1 周花半天实测**：能直连就纯前端实现；不能直连则增强模式退化为"复制条款到自己的对话工具里问"，或只留给未来的桌面版。别把设计建立在未验证的假设上。

## 9. 数据与隐私（技术亮点 5）

| 数据 | 存放 | 生命周期 |
|---|---|---|
| 原始文件 | 仅内存（File API） | 页面关闭即消失 |
| 解析文本、条款、结果 | 仅内存 | 同上 |
| 用户设置（地区、开关） | localStorage（无合同内容） | 持久 |
| API Key | localStorage 或每次手填 | 用户可清除，绝不进报告与日志 |
| 导出的报告 | 用户本地文件 | 用户自管 |

**不做**：IndexedDB 历史、云端同步、账号系统、任何遥测。

### 把承诺变成可验证的事实
README 里给出三种验证方式，并做成落地页的一个区块：

1. **断网使用**：基础功能完全可用（最强证明，建议做成主视觉）
2. **Network 面板**：打开开发者工具，全程零对外请求
3. **代码审计**：全局搜索 `fetch` / `XMLHttpRequest`，只应在增强模式那一处出现

这个设计在面试里非常好讲：**隐私不是我的政策条款，是我架构的推论，而且你可以自己验证。**

## 10. 用户流程与页面

```
1. 打开 → 首屏即上传区（不注册、不登录、不收集任何信息）
2. 选择地区（可从用人单位地址推断默认值）
3. 上传 PDF / Word；图片走 OCR + 用户核对修正
4. 本地分析（秒级，纯本地计算，无需等待网络）
5. 报告
   ├─ 综合评分
   ├─ 与当地范本的差异清单  ← 第一信息层级（v2 起置顶）
   ├─ 风险清单（红/黄/蓝，含原文、说明、法条原文、建议）
   ├─ 15 项关键信息（未约定的直接标出）
   └─ 三段总结（工资 / 工时 / 社保）+ 签署建议
6. 导出报告文件 / 复制话术 / [可选] 开启增强模式
```

15 项关键信息：工资结构、基本工资、绩效工资、奖金、发薪日期、工作时间、加班规则、休假制度、试用期、五险一金、合同期限、工作地点、违约责任、保密协议、竞业限制。

**报告页要像产品，不要像调试输出。** 这是面试官点开链接看到的第一屏，视觉质量直接影响印象分。

### 定位能力说明
- PDF：pdf.js 提供坐标，可做原文高亮
- Word / 图片：拿不到坐标，降级为**条款级引用**
- 这意味着切分正确率是关键指标（见第 7 节）

## 11. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Vite + React + TypeScript | 纯静态产物，轻；这个项目不需要 SEO 首屏渲染 |
| 样式 | Tailwind + shadcn/ui | 出视觉质量快，报告页体面 |

| Word | mammoth.js | 段落级结构足够支撑条款级引用 |
| 图片 OCR | WASM OCR（PaddleOCR-ONNX / tesseract.js） | **实验性**，中文与表格准确率低，必须配人工核对 |
| 规则引擎 | 纯 TypeScript，规则 JSON 声明 | 无依赖、可单测、便于贡献 |
| 范本比对 | 自研 | 核心资产 |
| 数据校验 | Zod / JSON Schema，CI 强制 | 保证数据质量 |
| 测试 | Vitest，规则库与比对引擎必须有单测 | 质量底线，也是加分项 |
| CI | GitHub Actions：lint + typecheck + test + 数据 schema 校验 | 绿色徽章是可信度的一部分 |
| 部署 | GitHub Pages（静态） | 零成本长期在线，简历里的活链接 |
| 离线版 | 单文件打包（vite-plugin-singlefile） | 双击即用，完全离线 |
| 分析埋点 | **无** | 无遥测，靠评测体系保证质量 |

## 13. README 与简历 / 面试叙事

对作品集项目，**这部分和代码同等重要**。做完不写清楚，等于没做。

### README 结构（建议）
1. 一句话是什么 + 一张报告页截图 + 活链接
2. 为什么不用大模型直接做（第 1 节的"30 秒回答"）
3. 架构图与数据流图
4. 核心算法：条款切分 → 归一化 → 对齐 → 四类差异
5. **准确率数据与评测方法**
6. 隐私：三种自证方式
7. 数据来源与版本可追溯性
8. 本地运行方式（三条命令内）
9. 已知局限（图片 OCR 准确率、地方覆盖范围、不构成法律意见）

**"已知局限"这一节不要省。主动写出局限，展示的是判断力，不是弱点。**

### 简历条目（可参考的写法）

> **劳动合同风险检查工具**（开源 · React + TypeScript · 在线演示）
> 面向应届生签约场景的纯本地合同审查工具。设计并实现基于官方示范文本的条款比对引擎（条款切分 → 语义归一化 → 对齐 → 四类差异分类），配合 30+ 条绑定了法律条文原文的风险规则；构建 30 份合同的人工标注评测集，召回率 xx%、精确率 xx%。采用无服务端架构，文件与解析结果全在浏览器内存中处理，断网可用，隐私承诺可逐行审计。

### 大概率会被问到的四个问题，及答案要点

**Q1：为什么不用大模型直接做？**
> 因为风险判断需要可复现和可解释，而模型输出做不到。核心是一个确定性比对引擎，结论可以追到具体条款和具体法条，还能写单测、算准确率。大模型只在最后一层做语义模糊的那几类判断，而且它不负责输出法条——法条一律从库里取，取完还要做四重引用校验。

**Q2：你怎么保证准确性？**
> 建了 30 份合同的标注集，用召回率和精确率衡量。我优先保召回率，因为漏报的代价远高于误报——漏掉一个违法违约金条款，用户可能真的签了。

**Q3：没有服务器，你怎么知道有人用、怎么迭代？**
> 拿不到使用数据，这是本地化架构的取舍，我用评测体系补偿：所有改进都在标注集上验证，指标不允许下降。用户的反馈走主动导出的脱敏报告或 GitHub issue。这个取舍我认为值得——合同含薪酬和个人信息，让用户上传到陌生服务器，很多人根本不会用。

**Q4：这算不算提供法律服务？**
> 不算，而且定位上我刻意做了区分。产品输出的是"你的合同与当地人社部门范本存在这处差异"以及对应的法律条文，是客观事实陈述和条文引用，不是我给出的法律意见。我不判断条款有效无效，也不预测结果，重大疑虑一律引导到 12333 或执业律师。

## 15. 需要你决定的事

**决定一：范本库选哪 3 个省。** 建议北京、上海、广东（生源与就业最集中）。
