## 后续：把文件格式补全（这是最硬的一块）

PDF 的文本层已经接上（`pdfjs-dist`，浏览器端，按需加载），坐标重组行的逻辑在引擎的 `src/text-lines.ts`（纯函数、有单测）。接新格式时的分工已经定好：**「文件 → 文本行」放在 `web/`，其余交给引擎**。

按价值与难度排序：

| 格式 | 难度 | 做法 |
|---|---|---|
| `.docx` | 已完成 | mammoth 的 `extractRawText`，产出"一段一行" |
| 直接粘贴 / PDF 文本层 | 已完成 | — |
| `.doc`（Word 97-2003） | 中 | `word-extractor` 在 Node 侧已能读，但**段落边界不可靠**；浏览器端能否打包运行未验证。也可以考虑引导用户另存为 .docx |
| 图片 / 扫描件 | **高** | 浏览器端没有可靠又免费的中文 OCR。诚实的做法是「尽力识别 + 用户核对修正」并明示准确率较低；不要用低准确率结果直接出报告 |

**图片这条路要单独立项想清楚**：它是真实场景里最常见的一种（学生拿到纸质合同拍照），但也是本地化架构下最难的一种。可选的折中：先做「上传图片 → 显示图片 → 用户照着录入或粘贴条款」，把工具做成录入辅助，而不是假装能自动识别。

## 一处需要留意的设计约定

法条与范本库里**只放能追溯到官方原文的内容**，规则库里的每条规则都必须绑定真实存在的法条 ID（`statuteRefs`），追溯不到的规则不写；规则里也不复制法条原文，报告要展示哪条就按 ID 从法条库取哪条。

这不是洁癖——作者不是法学专业，这条约束是把「个人法律判断」从系统里彻底移除的唯一办法。改这块代码时请保持这个约束。

**报告层同理：只做标注，不做评价。** 不给综合评分、不给签署建议，只把条款标出来并附上法律条文；签不签由用户自己判断。这条有测试钉住（报告里不含 `score` 与 `recommendation` 字段）。

## 抽取的原则：不要按形状猜（已被真实合同打穿三次）

| 真实打穿 | 当时按什么猜 | 正确做法 |
|---|---|---|
| 试用期工资取成 1500（绩效工资） | 金额取「这一条里最后一个」 | 按「试用期工资」标签锚定，取标签后第一个 |
| 发薪日期被判「合同未提及」 | 关键词只有「发薪／支付日期／发放日期」 | 覆盖真实写法，或干脆升级为事实抽「每月 X 日」 |
| 竞业限制 24312 个月 | `数字 + 年` 这个形状 | 标签锚定 + **合理性检查**：四位数字落在 1900–2200 是日历年份 |

两条硬要求：

1. **标签锚定**：靠标签（「试用期工资」「转正工资」「竞业限制期限」）决定取哪一项，而不是靠位置、顺序或形状。
2. **合理性检查**：荒谬值一律拒绝——期限不可能是 2026 年，工资不可能是 0 元。**宁可报「未识别」，也不给一个看起来合理实际错的值。**

为什么反复强调：这三处都是我读代码、编测试用例发现不了的。我自己编的用例里金额顺序总是对的、关键词总是规范的、不会混进日期。**只有真实合同能打穿它们**——继续收真实材料、把每一处错误变成回归测试，是提升这个工具最有效的办法。
