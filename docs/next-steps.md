## 下一步：范本比对引擎

**动手前必须知道的一条设计约束**：范本正文里有 143 处待填写位，抽取时被替换成 `{{FILL}}` 标记（见 `src/mark-blanks.ts`）。比对时 `{{FILL}}` 必须当作**通配符**，否则用户把内容填好的合同，每一处填空都会被判成"关键条款被改写"——误报率会高到不可用。正确做法是把范本条款编译成正则（`{{FILL}}` → `.+?`），再拿用户合同去匹配。

四类差异的判定建议：

| 差异类型 | 判定思路 |
|---|---|
| 范本有、合同没有 | 先按节标题与条文主题做**对齐**，对齐不上的才算缺失 |
| 范本没有、合同多了 | 合同里对不上范本任何条款的条文 |
| 关键条款被改写 | 对齐上了但正则匹配失败 |
| 填空留白 | 合同侧同一位置仍是空白（不是 `{{FILL}}` 对应的值） |

**对齐是真正的难点**：条款可能被合并、拆分、调整顺序。建议先做"节标题 + 关键词同义映射"的确定性对齐，不要一上来就上语义相似度——先把可解释、可测试的版本做出来，再考虑要不要加语义层。

## 范本覆盖度（待补）

目前只有 1 份：湖北省鄂州市梁子湖区的《劳动合同（通用）》。该份正文以 HTML 内联发布，所以管线走 HTML 分支，不需要 Word 解析。

要扩到更多地区，需要处理 **Word 97-2003 二进制 `.doc`**——实测北京、上海、广东、河南、沈阳、浙江、福州的官方范本基本都是 `.doc` 附件（少数是 `.docx`），网站正文里没有条款内容。纯 JS 读取器 `word-extractor` 已接入（`src/read-doc.ts`），能读出正文，**但它对段落边界的还原不可靠**（实测某市范本把"注意事项"六条连成了一行）。所以接入 `.doc` 范本前必须先验证段落边界，否则抽取会失败或错位。`.docx` 需要另加读取器（mammoth），尚未接。

另有两个已知的源页面瑕疵，都选择保持与来源一致、不做清理：

- 梁子湖区范本第三节工时制度处，正文里混入一个孤立的「方」字（原始 Word 排版残留）。
- 博湖县法条页面第 63 条多一个前引号。

## 一处需要留意的设计约定

法条与范本库里**只放能追溯到官方原文的内容**，规则库里的每条规则都必须绑定真实存在的法条 ID（`statuteRefs`），追溯不到的规则不写。这不是洁癖——作者不是法学专业，这条约束是把"个人法律判断"从系统里彻底移除的唯一办法。改这块代码时请保持这个约束。
