`src/diff-template.ts` 实现三级对齐（模式匹配 → 条号相同 → 相似度）与四类差异分类；`src/eval-diff.ts` 用已知答案的派生合同评测它，`npm run check` 里包含这一步。

## 下一步：把真实合同接进来

比对引擎目前只在"从范本派生的合同"上验证过，还没处理过真实合同。要接进来需要：

1. **合同侧条款抽取**。用户给的是 PDF / Word / 图片，不是我们的 HTML。`extract-template.ts` 可作为参考，但真实合同不保证有「一、」节标题、也不保证条号连续，所以要写一个更宽容的版本——至少要能在结构识别失败时退化成"段落即条款"，而不是像现在这样直接报错。
2. **PDF 文本层**：Node 侧可用 `pdfjs-dist`。注意真实 PDF 拿不到我们这种干净的 `<p>` 边界，段落还原会是主要难点。
3. **Word**：`.docx` 用 mammoth（尚未接），`.doc` 用已接入的 `word-extractor`（注意它段落边界不可靠）。
4. **图片**：本地 OCR 是本地化架构的固有短板，放最后，且必须配人工核对界面。

**建议先做一个小 CLI**：`npm run diff:contract -- <templateId> <合同文件>`，把差异打成可读清单。这样在动界面之前就能拿真实合同反复验证引擎，也避免把引擎缺陷带到界面阶段才发现。

## 范本覆盖度（待补）

目前只有 1 份：湖北省鄂州市梁子湖区的《劳动合同（通用）》。该份正文以 HTML 内联发布，所以管线走 HTML 分支，不需要 Word 解析。

要扩到更多地区，需要处理 **Word 97-2003 二进制 `.doc`**——实测北京、上海、广东、河南、沈阳、浙江、福州的官方范本基本都是 `.doc` 附件（少数是 `.docx`），网站正文里没有条款内容。纯 JS 读取器 `word-extractor` 已接入（`src/read-doc.ts`），能读出正文，**但它对段落边界的还原不可靠**（实测某市范本把"注意事项"六条连成了一行）。所以接入 `.doc` 范本前必须先验证段落边界，否则抽取会失败或错位。`.docx` 需要另加读取器（mammoth），尚未接。

另有两个已知的源页面瑕疵，都选择保持与来源一致、不做清理：

- 梁子湖区范本第三节工时制度处，正文里混入一个孤立的「方」字（原始 Word 排版残留）。
- 博湖县法条页面第 63 条多一个前引号。

## 一处需要留意的设计约定

法条与范本库里**只放能追溯到官方原文的内容**，规则库里的每条规则都必须绑定真实存在的法条 ID（`statuteRefs`），追溯不到的规则不写。这不是洁癖——作者不是法学专业，这条约束是把"个人法律判断"从系统里彻底移除的唯一办法。改这块代码时请保持这个约束。
